# synoptic

The agent-coordination host. It ships **Cortext**, an agent-neutral workflow and coordination capability delivered as a Substrate plugin, plus the skins that onboard Claude Code, Codex and OpenCode to it. The README maps the packages, and CONTRIBUTING.md covers PRs and labels.

## Layout

| Package | Published as | Notes |
|---|---|---|
| `packages/synoptic` | `@mnmal-ai/synoptic` | Harness-neutral host library: onboarding pipeline, cold-start projector, capability contract, handoff |
| `packages/cortext` | `@mnmal-ai/cortext` | Both Substrate plugins in one package. The coordinator plugin (`src/`) is the `cortext` namespace (Todos, Decisions, SessionLogs, AgentRules, Memory, Concepts, Councils); the kernel plugin `cortext-kernel` (`src/kernel/`, exported as `@mnmal-ai/cortext/kernel`) carries the schema constraints, migrations and body invariants. The manifest's `substrate.plugins` lists both |
| `packages/context-render` | `@mnmal-ai/context-render` | Type-generic index-and-pull rendering, body folding, budget trim, RRF ranking and rule tiering (must / pinned / salient / skim). Zero deps, no Node built-ins (both enforced by its tests). Synoptic uses its budget trim for hook-output ceilings |
| `packages/cortext-plugin` | *(not npm)* | The Claude Code skin for cortext. `private: true`, distributed through the `mnmal-ai` marketplace in `.claude-plugin/marketplace.json` |
| `packages/cortext-opencode` | `@mnmal-ai/cortext-opencode` | The OpenCode skin: cold-start injection via `experimental.chat.system.transform`, zero-dep committed `dist/plugin.js`. Published to npm because OpenCode installs plugins through Bun |
| `packages/cortext-codex` | *(not npm)* | Local Codex delivery |

This repo is the single source of the cold-start machinery and of the `substrate-conventions.md` fragment, including the copy in `.claude/`.

## Checks

```bash
pnpm install
pnpm build
pnpm check-types
pnpm lint
pnpm test
```

The pg-gated suites in `@mnmal-ai/cortext` skip without `POSTGRES_URL`. To run them, point it at a database whose name ends `_test` or `_dev`, reached as a role that is not a superuser and can write nothing outside test databases. The guards (`assertTestDatabase`, `assertNotSuperuser`, `assertCannotWriteOutsideTestDatabases`) come from `@mnmal-ai/substrate/testing`; `packages/cortext/test/_setup.ts` and `test/_global-setup.ts` call them. Do not re-inline them. CI's `pg` job shows the provisioning.

## Rules

- Inspect the installed implementation before assuming API behaviour.
- Keep changes small and testable, and prefer evidence over documentation.
- Local-first: no SaaS dependency, no telemetry, no network beyond the configured model and Substrate endpoints.
- Prefer inspectable state (JSONL or SQLite over opaque formats), deterministic selection and reversible changes.
- **Lint is CI-enforced** through the root `biome.json`. Its `files.includes` exclusions are load-bearing, notably `!**/config.schema.json`: that file is generated by `z.toJSONSchema()` and compared byte-for-byte by `schema-parity.test.ts`.
- **`hooks/*.mjs` and every `bin/*.mjs` in `cortext-plugin` are committed build artifacts**, as is `cortext-opencode/dist/`. That includes `hooks/inbox-watch.mjs`, `hooks/inbox-bridge.mjs` (built from `src/inbox-bridge.ts` with `claude-code` external) and the bins `resolve-fragment`, `audit`, `prune-cache` and `onboard` (`tsdown.config.ts`). `pnpm build` regenerates them, the build is byte-deterministic, and CI fails if a build changes tracked files. Each is excluded by name in `biome.json`.

## What a change reaches

Four distribution layers, and a change usually touches one. A release can legitimately reach nobody.

| You changed | It reaches a consumer via | Which needs |
|---|---|---|
| `packages/cortext/src`, including `src/kernel` | npm tarball, loaded by a Substrate runtime from `SUBSTRATE_PLUGIN_DIR` | publish **and** a runtime deploy |
| `packages/context-render/src` | npm tarball; also inlined into `cortext-plugin/hooks/*.mjs` via synoptic | publish, and for the hooks the row below |
| `packages/synoptic/src`, `packages/cortext-plugin/{hooks/hooks.json,types/}` | rebuilt `cortext-plugin/hooks/*.mjs` → this repo's marketplace, `git-subdir` at the release tag | publish, then a marketplace + plugin update on each box |
| `packages/cortext-plugin/fragments/` | the installed `.claude/substrate-conventions.md` in each consumer repo | the above, plus `/substrate-setup` re-run per repo, and only if the content digest changed |
| `pnpm-workspace.yaml`, root docs, `biome.json`, CI | nothing, repo-local | nothing |

**Skins ride one tag.** The Claude plugin is served from this repo's marketplace, `.claude-plugin/marketplace.json`, as a `git-subdir` pinned to a synoptic tag, and `@mnmal-ai/cortext-opencode` publishes on the same release, so every release bumps every skin. The `version` script stamps `package.json`'s version into `plugin.json` and into the marketplace's `ref`, so the release PR carries its own repin; `release-alignment.test.js` fails if the ref and the version disagree. Between the merge and the tag the ref names a tag that does not exist yet, so an install in that window fails rather than serving unreleased code.

To check whether a release ships anything, run `git diff <last-tag>..HEAD -- packages/`. Empty means byte-identical artifacts. **Published** (on the registry), **pinned** (the marketplace names the tag) and **live** (a runtime serves it) are separate states.

`scripts/check-release-class.mjs` is a manual guard that sizes a bump against `packages/cortext/release-surface.json`. See `scripts/README.md`.

## The Substrate compatibility contract

Cortext declares one peer dependency, `@mnmal-ai/substrate`, never a `dependency`. The range is one literal, `SUBSTRATE_CONTRACT_RANGE` in `packages/cortext/src/kernel/substrate-contract.ts`, and it must hold in three places, each checked at a different moment:

| Artifact | Checked by | When |
|---|---|---|
| `contractVersion` on both plugin objects | the Substrate loader | boot |
| the `@mnmal-ai/substrate` peer range in the manifest | the package manager | install |
| `deps.neverBundle` in `tsdown.config.ts` | the bundler | build |

They are not redundant: `SUBSTRATE_PLUGIN_DIR` scans a directory, so a hand-dropped plugin never meets a package manager and only the loader check remains. `substrate-contract-parity.test.ts` enforces all three, including that the catalog resolves inside the range.

**The ceiling tracks compatibility, not major boundaries.** Widen it only after reading, and running the suites against, what the new major changed, including the types the plugins construct. Never widen past a major you have not read: npm publishes are immutable, and a ceiling admitting a breaking major loads a plugin that misbehaves with the loader check passing. Narrowing below the running binary's major makes the loader refuse the plugin and the server fail to boot.

**A contract widening clears only `@mnmal-ai/cortext`.** `@mnmal-ai/synoptic` speaks HTTP and declares no Substrate peer, so the contract check cannot see wire-shape changes it depends on.

**An undeclared runtime import is silently inlined.** tsdown bundles anything not in `dependencies`, `peerDependencies` or `neverBundle`, and an inlined package leaves no specifier in `dist/` to grep for. The parity test therefore checks from the import graph towards the manifest.

## Substrate version bumps

A catalog bump does not move the published contract; it changes only what local dev and CI resolve, which must stay inside `SUBSTRATE_CONTRACT_RANGE`. Bump the one `@mnmal-ai/substrate` catalog entry and follow the waiver comment in `pnpm-workspace.yaml` for `minimumReleaseAgeExclude`.

`compose()` is called from test files only; the Substrate binary does the composing in production. Breaking changes to `compose()` land as test failures, not runtime risk.

## Releases

synoptic has its own version line; a synoptic version implies nothing about any Substrate version. Bump versions on a `release/vX.Y.Z` branch. Merging it to `main` publishes through `publish.yml`, using npm trusted publishing behind the protected `release` environment, then tags. Never tag or publish by hand. Until 1.0.0, prereleases go to npm's `next` tag.

`@mnmal-ai/*` packages are public on npmjs.com, so installs need no token. The repo `.npmrc` only pins the `@mnmal-ai` scope to npmjs.
